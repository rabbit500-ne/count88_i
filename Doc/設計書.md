# カウントアルゴリズム
## 基本戦略
探索木を階層的に分割し、幅優先探索（BFS）で並列化ポイントを作り、深さ優先探索（DFS）で終局までカウントする。

## 幅優先探索（BFS）
目的: 局面ツリーを特定深さまで展開し、並列計算可能なタスクに分割

アルゴリズム:
```
function BFS(start_position, target_depth):
    queue = [start_position]
    result_positions = {}
    
    for depth in 0 to target_depth:
        next_queue = []
        for position in queue:
            for move in legal_moves(position):
                next_pos = apply_move(position, move)
                if next_pos not in result_positions:
                    result_positions[next_pos] = 0
                result_positions[next_pos] += 1
                next_queue.append(next_pos)
        queue = next_queue
    
    return result_positions  # {局面: 到達パス数}
```

パラメータ:
- `start_position`: 開始局面（64bit ビットボード × 2）
- `target_depth`: 展開する深さ（推奨: 6-8手）

出力:
- 到達可能局面のリスト
- 各局面への到達パス数（重複カウント用）

計算量: O(b^d)
- b: 平均分岐数（約10）
- d: 探索深さ

## 深さ優先探索（DFS）
目的: 指定局面から終局までの棋譜総数をカウント

アルゴリズム:
```
function DFS(position, memo={}):
    if position in memo:
        return memo[position]
    
    if is_game_over(position):
        return 1
    
    legal = legal_moves(position)
    if len(legal) == 0:  # パス
        return DFS(pass_turn(position), memo)
    
    total = 0
    for move in legal:
        next_pos = apply_move(position, move)
        total += DFS(next_pos, memo)
    
    memo[position] = total
    return total
```

パラメータ:
- `position`: 開始局面

出力:
- 終局までの棋譜総数（BigInt / 多倍長整数）

最適化:
- メモ化（転置表）
- 枝刈り（明らかに無効な手を排除）

## 分散計算フロー
表記：深さをスタート地点をD0とする。D1はD0+1の深さ。D00-06 はD0からD6の深さまでのこと。幅探索で作成したツリーを探索セグメントと呼ぶ。メモリの関係で1つのセグメントは10MB以下になるように設定する。とりあえず6手で区切る。

D00-06 セグメント
D06-12 セグメント
D12-18 セグメント
D18-24 セグメント
D24-30 セグメント
D30-36 セグメント
D36-42 セグメント
D42-48 セグメント
D48-54 セグメント
D54-60 セグメント
D60-66 セグメント
D66-72 セグメント
D72-78 セグメント
D78-84 セグメント
D84-90 セグメント

### フェーズ1: セグメント作成
1. ルート局面（初期配置）からD36-42の深さまでBFS実行して探索セグメントを作成する。セグメントは２つのセグメントを派生させる。

### フェーズ2: 中間分割（深さ D1 → D1+D2）
1. フェーズ1の各局面から再度BFS実行
2. 深さD2（例: 6手）まで展開
3. 新たな中間局面をタスクキューに投入

例: 10^7 × 10^6 = 10^13 個の葉局面

重要 - メモリ管理戦略:
- フェーズ2では全局面を一度にメモリ展開すると膨大なメモリが必要
- ストリーミング処理: 以下の2つのみをメモリに保持
  - `current`: 現在処理中のBFSタスク結果
  - `next`: 次に実行されるBFSタスク
- 処理完了後は即座にタスクキューへ投入し、メモリから解放
- 全体をバッチ処理せず、逐次的に処理することでメモリ使用量を抑制

### フェーズ3: 終局カウント（深さ D1+D2 → 終局）
1. フェーズ2の各葉局面からDFS実行
2. 終局までの棋譜数をカウント
3. 結果をDBに保存

### フェーズ4: 集約
1. 全DFS結果を合算
2. 到達パス数を考慮して正確な総数を算出

```
総棋譜数 = Σ(各葉局面の到達パス数 × その局面からの棋譜数)
```

## パラメータ調整指針
| パラメータ | 推奨値 | 考慮点 |
|----------|--------|--------|
| BFS初期深さ (D1) | 6-8手 | タスク数とメモリのバランス |
| BFS中間深さ (D2) | 5-7手 | 葉局面数の管理 |
| DFS開始深さ | 12-15手 | 1タスクの計算時間（目安: 1-10秒） |
| タスクタイムアウト | 60秒 | ネットワーク遅延を考慮 |

ベンチマーク必須: 実環境で最適値を測定

# データ構造の内部実装
## ビットボード実装
局面は64bitビットボード×2で表現します。黒石と白石それぞれを64bit整数で表現し、1が石がある位置、0が空き位置を表します。

ビットボード操作:
- 合法手の生成: ビット演算で高速に実現
- 着手処理: XOR演算で石の反転を実現
- 局面比較: ハッシュ値で高速比較

## 多倍長整数の扱い
JavaScript: `BigInt`型を使用
Python: 組み込み`int`型（自動的に多倍長整数として扱われる）
データベース: `NUMERIC(80, 0)`型（最大80桁の整数）

API通信時は文字列形式で送受信し、JSON互換性を確保します。

# 実装上の課題と対策
## メモリ使用量の制御
課題: BFS展開時にメモリ不足が発生する（特にD2階層）

対策:
- ストリーミング処理の採用
  - 全局面を一度にメモリ展開しない
  - `current`（処理中）と`next`（次のタスク）のみを保持
  - 処理済みタスクは即座にキューへ投入し解放
- 段階的処理
  - バッチサイズを制限（例: 1000タスク/バッチ）
  - メモリ使用量の監視とダイナミック調整
- ディスク活用
  - 大量の中間結果は一時的にDBまたはファイルに保存
  - 必要に応じてページング処理

## 重複局面の排除
課題: 異なる手順で同一局面に到達

対策:
- Zobrist Hashing による高速比較
- 転置表（Transposition Table）の活用

## 計算結果の検証
課題: クライアント側の計算ミスや不正

対策:
- ランダムに5-10%のタスクを複数クライアントに重複配布
- 結果が一致しない場合は再計算

## タスク失敗時のリトライ
課題: ネットワーク断やブラウザクローズ

対策:
- タスクタイムアウト（60秒）後に自動再配布
- 3回失敗したタスクは優先度下げ

## 数値オーバーフロー
課題: 10^58 は64bit整数を超える

対策:
- BigInt / 多倍長整数の使用
- 文字列での転送（JSON互換性）
